# マニュアルの要点

Claude はこのファイルの制約を最優先で守る。原文は `notes/manual-full.md`（認証情報だけ伏せてある）。

## 題材
- アプリの概要: ISUReal。写真共有 SNS。投稿期間（posting window）の開始通知を SSE（`GET /api/notifications`）で受け、自分が投稿してから友達の投稿を見る。コメント、RealMoji（顔写真リアクション）、Memories、エクスポートあり
- 主な登場人物: 一般利用者（SecretKey でログイン、region は asia/europe/america）、認定公開アカウント（一方向フォロー可）、管理者 `admin`（ベンチが投稿期間の開始に使う。変更・削除禁止）
- 時間内投稿は投稿期間の `onTimeDeadline` で判定。期限後も期間終了までは投稿可。`lateSeconds` は秒未満切り捨て、時間内なら 0

## スコア計算式
- `スコア = Σ(採点件数 × 配点 × リージョン倍率)`。倍率 asia 1 / europe 1.5 / america 1.5（加点時点の所属リージョン）。小数点以下切り捨て
- 加点の大きいもの: 投稿後の友達フィード検証通過 10（最後の投稿期間は 20）、エクスポート 20、RealMoji 送信 5、退会 5、コメント 3、プロフィール画像変更・削除 3、Memories 月単位 3。他は 1〜2
- 友達フィード検証は「投稿が受理され、その投稿期間の終了前に友達フィードの検証に成功」で 1 ユーザー × 1 投稿期間 1 回
- 投稿期間ごとの閲覧加点上限: 1 人あたりフィード 20、画像 4、投稿詳細 8、RealMoji・コメント一覧 8、プロフィール 4。RealMoji 送信・コメントは各 5 回まで
- 減点: エラー件数による直接の減点はなし。`503` はベンチが再試行するが、エラー率や応答時間の計測からは除外されない
- fail（走行 FAIL = 0 点）になる条件:
  - `POST /api/initialize` または整合性チェックの失敗
  - 初期データユーザーのログインが 401
  - フィードに存在しない投稿・閲覧権限のない投稿が出る／閲覧権限のない投稿を取得できる
  - 閲覧権限のない投稿への RealMoji、コメント権限のない投稿へのコメントが受理される
  - Memories・エクスポートの履歴や画像が初期データの期待値と一致しない
  - 投稿削除成功から 5 秒を過ぎても画像を取得できる

## 反映の猶予・整合性
- 書き込み成功後の読み取りには即反映（リージョンをまたいでも同じ）。**猶予は「削除した投稿の画像」の 5 秒だけ**。公開範囲・友達関係・ブロックの反映には猶予なし
- キャッシュしてよいもの: 上記を満たす範囲のみ。それ以外は更新時に必ず無効化（3 台のアプリ間でも整合が必要）
- 画像 URL の署名・期限の形式と検証結果は変更禁止。不正署名・期限切れ・無効画像は `403`
- ベンチは HTTP リダイレクトを追わない

## 初期化
- `POST /api/initialize`。DB は `~/webapp/sql/init.sh` でも初期化できる
- 追加したデータ構造・キャッシュ・複製先も含め、全リージョンで整合した初期状態に戻す。初期データの履歴と画像も取得できる状態を保つ
- 時間制限: 具体的な秒数は記載なし（「最終チェックで確定する制限時間内」）
- レスポンスは空でない `language` を含める（`lang` ではない）。例: `{"language":"go","agent":"human","harness":"manual","model":"brain"}`。agent/harness/model は申告用で採点に無関係（Claude を使うなら合わせて書き換える）

## サーバー構成
- asia1（nginx + Go、asia）、europe1（nginx + Go、europe）、america1（nginx + Go、america）、asia2（共有 PostgreSQL 16、asia）、ルーター（触れない）
- ルーターが `X-Country-Code` でリージョン別に振り分ける（省略時は JP → asia1）。リージョン間には遅延と帯域制限あり。asia1 と asia2 は同一リージョン扱い
- クライアント IP は `X-Client-IP` を使う
- DB 接続情報は `/home/isucon/env.sh`。初期状態では全アプリが asia2 に接続
- 全台を使う構成。サーバーのリージョン変更不可
- 変更してよいもの: サーバー内のソフトウェア、DB スキーマ、インデックス、保存方式、実装、キャッシュ、別言語での再実装、セキュリティグループ（新しいポートの開放のみ）
- 変えてはいけないもの: URI・メソッド・ステータス・JSON/HTML の構造と意味、配布静的ファイルの内容、認証・閲覧制限・公開範囲・削除・画像署名の検証結果、初期データ、初期化処理、ブラウザからの利用

## メンテナンス用コマンド・禁止事項
- 環境チェック: `sudo /usr/local/bin/envcheck`（各 4 台）。設定変更後に実行する
- 変更・削除禁止: `/usr/local/bin/envcheck`、`/usr/local/bin/isucon-contest-envcheck`、`/etc/systemd/system/envcheck.service`、`/etc/systemd/system/envcheck-baseline.service`、`/etc/isucon/envcheck.json`、`/var/lib/isucon-envcheck/`、`isucon-register.service` 関連、`isuadmin` ユーザー関連、isucon 以外のユーザーと公開鍵
- セキュリティグループで SSH(22)、HTTPS(443)、ルーター HTTP(8080) は変更しない
- **ルーターを迂回するサーバー間通信は禁止**。遅延・帯域制限の回避も禁止。DB 接続などサーバー間通信もルーター経由のまま
- ベンチマーカーだけを識別して挙動を変える実装、固定応答で整合性検証を回避する実装は禁止
- 管理者アカウントの削除・変更禁止
- 追試: 4 台 + ルーター再起動 → envcheck → ベンチ（最終スコアの 75% 以下か FAIL が 3 回で失格）→ 再起動 → 書き込みデータが残っているか確認 → ブラウザ表示確認
- 競技終了時に 4 台とも起動していること。スタックを複数混在させない

## 調整できそうなつまみ（間隔、件数、タイムアウトなど）
- 投稿期間の開始は管理者（ベンチ）が行うので、アプリ側で間隔を調整する余地は不明。コードを読んで確認する
- europe/america は倍率 1.5。リージョン間の遅延があるので、europe1・america1 から asia2 の DB へのアクセス回数を減らすのが効きそう（ただしルーター経由は維持）
